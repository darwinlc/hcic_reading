The gcloud command pattern
gcloud <service> <resource> <verb> <name> [--flags]
Read it left-to-right: tool → service → what → action → target → options
Example: gcloud functions logs read my-function --region=us-central1 --limit=50
Three tools — three domains
gcloud → infrastructure (Functions, Run, Scheduler, IAM, Secrets) bq → BigQuery only (query, load, show, mk, rm) gsutil → Cloud Storage (ls, cp, mb, rb, cat)
AUTH

Auth & Config — always run first

Login & set project
# Interactive browser login gcloud auth login # ADC — used by SDKs (Python, Node) when running locally gcloud auth application-default login # Set default project for all commands gcloud config set project my-project-id gcloud config get-value project # verify # Identity token — needed for calling authenticated HTTP functions TOKEN=$(gcloud auth print-identity-token)
ADC vs Identity Token:
application-default login → for local SDK calls (BigQuery, GCS, Secret Manager from your Python script).
print-identity-token → for authenticating HTTP requests to Cloud Functions / Cloud Run.
FUNCTIONS

Cloud Functions — serverless compute

Role in architecture: API endpoints, crawlers, loaders, emailers. Each function is one HTTP endpoint or one scheduled job. Gen 2 = Cloud Run under the hood; supports up to 60 min timeout.
Deploy
gcloud functions deploy my-function \ --gen2 \ --runtime=python311 \ # or nodejs20, go122, java21 --region=us-central1 \ --source=./functions/my-function \ # local directory with main.py --entry-point=handler_fn \ # Python function name --trigger-http \ --no-allow-unauthenticated \ # require identity token --set-env-vars GCP_PROJECT=$(gcloud config get-value project) \ --memory=512MB \ --timeout=3600s # Gen 2 max
Call (authenticated)
TOKEN=$(gcloud auth print-identity-token) PROJECT=$(gcloud config get-value project) curl -s -X POST \ -H "Authorization: Bearer ${TOKEN}" \ "https://us-central1-${PROJECT}\ .cloudfunctions.net/my-function\ ?param=value"
Logs & manage
# Stream recent logs gcloud functions logs read my-function \ --region=us-central1 \ --limit=50 # List all functions gcloud functions list \ --region=us-central1 # Delete gcloud functions delete my-function \ --region=us-central1
FlagWhen to use
--allow-unauthenticatedPublic endpoints (login page, webhooks). Omit for everything else.
--set-env-vars KEY=VALNon-secret config (project ID, dataset name, region)
--set-secrets KEY=SECRET:latestPull from Secret Manager at deploy time — preferred over env vars for credentials
--min-instances 1Eliminate cold starts for latency-sensitive APIs (costs money)
--concurrency 80Gen 2 only — how many requests one instance handles simultaneously
SCHEDULER

Cloud Scheduler — cron triggers

Role in architecture: Fires HTTP requests to Cloud Functions on a cron schedule. Think of it as a managed crontab that calls your functions.
Create a scheduled job
gcloud scheduler jobs create http my-job \ --location=us-central1 \ --schedule="0 21 * * *" \ # cron: 9 PM daily --time-zone="Asia/Singapore" \ --uri="https://us-central1-${PROJECT}.cloudfunctions.net/my-function" \ --http-method=POST \ --oidc-service-account-email=SA_EMAIL # auth the call
Day-to-day operations
# List all jobs gcloud scheduler jobs list \ --location=us-central1 # Trigger immediately (fire-and-forget) gcloud scheduler jobs run my-job \ --location=us-central1 # Pause / resume gcloud scheduler jobs pause my-job \ --location=us-central1 gcloud scheduler jobs resume my-job \ --location=us-central1
Cron quick reference
# ┌ min ┬ hour ┬ day ┬ mon ┬ weekday # │ │ │ │ │ 0 21 * * * # 9 PM daily 0 */4 * * * # every 4 hours 30 9,13,17 * * * # 9:30, 1:30, 5:30 0 9 * * 1 # 9 AM every Monday 0 0 1 * * # midnight 1st of month
Tip — fire-and-forget vs waiting: gcloud scheduler jobs run fires the HTTP request and returns immediately — it does not wait for the function to finish. To see the result, check function logs after.
BIGQUERY

BigQuery — analytics & ML feature store

Role in architecture: Stores all structured data — OHLCV, option chains, ML features, model outputs. Queried by API functions and Vertex AI training jobs. Partitioned tables keep query costs low.
Query from terminal
# Interactive query bq query --nouse_legacy_sql \ 'SELECT ticker, COUNT(*) AS n FROM myproject.options_data.option_chain GROUP BY 1' # Save result to a table bq query --nouse_legacy_sql \ --destination_table=myproject:ml_features.daily_summary \ --replace \ 'SELECT DATE(snapshot_ts) AS dt, AVG(iv) AS avg_iv FROM ...'
Datasets & tables
# Create dataset bq mk --location=US my_dataset # Describe table schema bq show myproject:my_dataset.my_table # List tables in dataset bq ls my_dataset # Delete table bq rm -f my_dataset.my_table
Load data
# Load CSV from GCS bq load \ --autodetect \ --source_format=CSV \ my_dataset.my_table \ gs://my-bucket/data/*.csv # Load gzip CSV bq load \ --source_format=CSV \ my_dataset.my_table \ gs://my-bucket/data/*.csv.gz
PatternWhy it matters
PARTITION BY DATE(ts)Queries with a date filter scan only matching partitions — huge cost saving as data grows
CLUSTER BY ticker, expirationFurther reduces bytes scanned when filtering by those columns
@param in queriesUse ScalarQueryParameter in Python SDK — prevents SQL injection, never use f-strings for values
LIMIT 1000Always cap ad-hoc queries to avoid accidentally scanning the full table

SECRETS

Secret Manager — credentials & API keys

Role in architecture: Stores credentials that functions need at runtime — SMTP passwords, external API keys, service account keys. Functions fetch secrets via SDK or have them injected as env vars at deploy time. Never hardcode secrets or put them in .env.yaml committed to git.
Create & update secrets
# Create new secret echo -n "my-secret-value" | \ gcloud secrets create my-secret \ --data-file=- # Add a new version (rotate) echo -n "new-value" | \ gcloud secrets versions add my-secret \ --data-file=-
Read & manage
# Read latest version gcloud secrets versions access latest \ --secret=my-secret # List all secrets gcloud secrets list # Verify secret exists gcloud secrets describe my-secret
Inject secret into Cloud Function at deploy time (preferred)
gcloud functions deploy my-function \ --set-secrets SMTP_PASSWORD=gmail-app-password:latest \ # becomes env var inside function --set-secrets API_KEY=coingecko-api-key:latest \ ...
IAM

IAM — who can do what

Role in architecture: Controls which service accounts (functions, Vertex AI jobs) can access which resources (BigQuery, GCS, Secret Manager). Cloud Scheduler uses a service account to authenticate calls to your functions.
Service accounts
# Create service account gcloud iam service-accounts create \ my-sa \ --display-name="My Service Account" # List service accounts gcloud iam service-accounts list # Get App Engine default SA email gcloud iam service-accounts list \ --filter="displayName:App Engine" \ --format="value(email)"
Grant roles
# Grant BigQuery access to a function's SA gcloud projects add-iam-policy-binding \ ${PROJECT} \ --member="serviceAccount:SA_EMAIL" \ --role="roles/bigquery.dataEditor" # Allow Scheduler SA to invoke function gcloud functions add-invoker-policy-binding \ my-function \ --member="serviceAccount:SA_EMAIL" \ --region=us-central1
Common roleWhat it allows
roles/bigquery.dataEditorRead + write BQ tables (used by loader/crawler functions)
roles/bigquery.jobUserRun BQ queries (needed alongside dataEditor)
roles/storage.objectAdminRead + write GCS objects
roles/secretmanager.secretAccessorRead secret versions (functions that fetch API keys)
roles/cloudfunctions.invokerCall authenticated HTTP functions (used by Scheduler SA)
roles/aiplatform.userSubmit Vertex AI training jobs + call endpoints

CONTAINERS

Containers — the concept before the commands

What is a container?
A container packages your code plus everything it needs to run (Python version, libraries, system deps) into a single portable image. You build it once; it runs identically on your laptop, Cloud Run, GKE, or Vertex AI.

Think of it like a shipping container: the contents (your app) are sealed inside a standard box that any ship (GCP service) can carry — no "it works on my machine" problems.
The container lifecycle
Write Dockerfile → build image → push to registry → run anywhere (recipe) (snapshot) (Artifact Registry) (Run / GKE / Vertex)
Minimal Dockerfile for a Python Cloud Run service
# Start from an official base — Python 3.11 already installed FROM python:3.11-slim WORKDIR /app # Install deps first (Docker layer-caches this if requirements.txt unchanged) COPY requirements.txt . RUN pip install --no-cache-dir -r requirements.txt # Copy your code COPY . . # Tell Cloud Run what port your app listens on ENV PORT=8080 CMD ["python", "main.py"]
Build & run locally (Docker CLI)
# Build image, tag it docker build -t my-app:latest . # Run locally on port 8080 docker run -p 8080:8080 my-app:latest # Run with env vars docker run -p 8080:8080 \ -e GCP_PROJECT=my-project \ my-app:latest # Open a shell inside a running container docker exec -it CONTAINER_ID bash
Key Docker concepts
# Image — the blueprint (read-only snapshot) docker images # Container — a running instance of an image docker ps # running docker ps -a # all (incl. stopped) # Layers — each Dockerfile line = one layer # Docker caches layers; put slow steps early # (e.g. pip install before COPY . .) # Logs from a running container docker logs -f CONTAINER_ID
REGISTRY

Artifact Registry & Cloud Build — store & build images in GCP

Artifact Registry is GCP's private Docker registry — like Docker Hub but inside your project. Cloud Run, GKE, and Vertex AI pull images from here.

Cloud Build builds your image in the cloud (no local Docker needed). It reads your Dockerfile, builds, and pushes to Artifact Registry in one command.
One-time setup — create a repository
gcloud artifacts repositories create my-repo \ --repository-format=docker \ --location=us-central1 \ --description="App container images" # Configure Docker to authenticate with GCP registry gcloud auth configure-docker us-central1-docker.pkg.dev
Build & push manually (local Docker)
PROJECT=$(gcloud config get-value project) IMAGE=us-central1-docker.pkg.dev/${PROJECT}/my-repo/my-app # Build and tag with registry path docker build -t ${IMAGE}:latest . # Push to Artifact Registry docker push ${IMAGE}:latest
Build in the cloud (no local Docker)
PROJECT=$(gcloud config get-value project) IMAGE=us-central1-docker.pkg.dev/${PROJECT}/my-repo/my-app # Cloud Build: uploads source, builds, pushes gcloud builds submit \ --tag ${IMAGE}:latest . # Check build history gcloud builds list --limit=5
Manage images in Artifact Registry
# List images in your repo gcloud artifacts docker images list \ us-central1-docker.pkg.dev/${PROJECT}/my-repo # Delete old image versions (keep storage costs down) gcloud artifacts docker images delete \ us-central1-docker.pkg.dev/${PROJECT}/my-repo/my-app:old-tag \ --delete-tags
CLOUD RUN

Cloud Run — managed containers, no servers

Role in architecture: Runs any containerised app as a scalable HTTP service — your React API backend, a FastAPI ML serving layer, or a long-running data processor. Cloud Functions Gen 2 actually runs on Cloud Run under the hood.

vs Cloud Functions: Use Cloud Run when you need a web framework (FastAPI, Flask), WebSockets, longer cold start control, or a custom base image. Use Cloud Functions for simple event handlers and scheduled jobs.
Deploy pattern
build image → push to Artifact Registry → gcloud run deploy → get HTTPS URL
Deploy a container to Cloud Run
gcloud run deploy my-service \ --image=us-central1-docker.pkg.dev/${PROJECT}/my-repo/my-app:latest \ --region=us-central1 \ --platform=managed \ --no-allow-unauthenticated \ # or --allow-unauthenticated for public --set-env-vars GCP_PROJECT=${PROJECT} \ --set-secrets API_KEY=my-secret:latest \ --memory=1Gi \ --cpu=1 \ --min-instances=0 \ # 0 = scale to zero when idle --max-instances=10 \ --timeout=3600 # max request timeout (seconds)
Manage services
# List all services gcloud run services list \ --region=us-central1 # Get service URL gcloud run services describe my-service \ --region=us-central1 \ --format="value(status.url)" # Delete service gcloud run services delete my-service \ --region=us-central1
Revisions & traffic splitting
# List revisions (each deploy = new revision) gcloud run revisions list \ --service=my-service \ --region=us-central1 # Canary: send 10% to new revision gcloud run services update-traffic \ my-service \ --region=us-central1 \ --to-revisions=my-service-v2=10,LATEST=90
ConceptHow it works
Scale to zero--min-instances=0 — shuts down when idle, cold start on first request (~1–3s). Set --min-instances=1 to eliminate cold starts.
ConcurrencyOne container instance handles multiple requests simultaneously (default 80). Unlike Functions where one instance = one request.
RevisionEvery deploy creates a new immutable revision. You can roll back by shifting traffic to an older revision.
PORT env varCloud Run injects PORT (default 8080). Your app must listen on that port — not hardcoded 5000 etc.
GKE

GKE (Kubernetes) — when Cloud Run isn't enough

What is Kubernetes?
Kubernetes (K8s) is an orchestrator — it manages many containers across many machines, handles failures, scales them up/down, and routes traffic between them. GKE = Google's managed Kubernetes; you don't manage the control plane, just your workloads.

When to use GKE over Cloud Run:
• You need GPU nodes for ML inference  |  • You have stateful workloads (databases, queues)
• You need fine-grained networking (sidecars, service mesh)  |  • Multi-container pods (e.g. app + metrics exporter)
• You're running 24/7 workloads where Cloud Run's per-request billing is more expensive than reserved nodes
Core Kubernetes concepts
Pod — smallest unit; one or more containers sharing network + storage Deployment — manages N identical pods; handles rollouts and restarts Service — stable internal IP/DNS for a set of pods (load balances between them) Ingress — external HTTP(S) entry point → routes to Services Namespace — logical isolation within a cluster (e.g. prod vs staging) ConfigMap — non-secret config key/value pairs Secret — sensitive config (passwords, tokens) — use GCP Secret Manager instead when possible
Cluster setup
# Create an Autopilot cluster (GKE manages node sizing automatically — recommended for beginners) gcloud container clusters create-auto my-cluster \ --region=us-central1 # Get credentials — writes to ~/.kube/config so kubectl works gcloud container clusters get-credentials my-cluster \ --region=us-central1 # List clusters gcloud container clusters list
kubectl — the Kubernetes CLI
# kubectl follows the same pattern as gcloud: # kubectl <verb> <resource> [name] # Show everything running kubectl get pods kubectl get deployments kubectl get services # Describe a pod (events, errors) kubectl describe pod my-pod-xyz # Logs from a pod kubectl logs -f my-pod-xyz # Shell into a running pod kubectl exec -it my-pod-xyz -- bash
Deploy an app to GKE
# Apply a YAML manifest (declarative) kubectl apply -f deployment.yaml # Scale a deployment kubectl scale deployment my-app \ --replicas=3 # Roll out a new image kubectl set image deployment/my-app \ my-app=${IMAGE}:v2 # Roll back to previous version kubectl rollout undo deployment/my-app # Watch rollout status kubectl rollout status deployment/my-app
Minimal deployment.yaml — what a deploy manifest looks like

PUB/SUB

Pub/Sub — async messaging between services

Role in architecture: Decouples services so they don't call each other directly. Example: crawler publishes a "new file ready" message → loader subscribes and triggers automatically, without needing Cloud Scheduler at all. Also useful for fan-out: one event triggers multiple downstream functions simultaneously.

vs Cloud Scheduler: Scheduler is time-based (every 4h). Pub/Sub is event-based (trigger immediately when something happens).
The pattern
Publisher (crawler) → Topic → Subscription → Subscriber (loader / emailer) └─ push: Pub/Sub calls your function's URL └─ pull: your function polls the subscription
Create topic & subscription
# Create topic gcloud pubsub topics create new-file-ready # Push subscription → calls a Cloud Function gcloud pubsub subscriptions create loader-sub \ --topic=new-file-ready \ --push-endpoint=https://us-central1-${PROJECT}\ .cloudfunctions.net/load_option_chain \ --ack-deadline=600 # seconds to process
Publish & inspect
# Publish a test message gcloud pubsub topics publish new-file-ready \ --message='{"blob":"optionchain/20260517.csv.gz"}' # Pull messages manually (debug) gcloud pubsub subscriptions pull loader-sub \ --limit=5 \ --auto-ack # List topics / subscriptions gcloud pubsub topics list gcloud pubsub subscriptions list
OPS

Cloud Logging & Monitoring — observability

Cloud Logging collects logs from every GCP service automatically. gcloud functions logs read is just a shortcut into it.
Cloud Monitoring tracks metrics (CPU, memory, request counts, error rates) and fires alerts when thresholds are crossed.
Logging — query logs from terminal
# All logs from a Cloud Function gcloud logging read \ 'resource.type="cloud_run_revision" resource.labels.service_name="my-function"' \ --limit=50 \ --format="value(textPayload)" # Only errors in last 1 hour gcloud logging read \ 'severity=ERROR timestamp>="2026-05-17T00:00:00Z"' \ --limit=20 # BQ loader errors only gcloud functions logs read option-chain-bq-loader \ --region=us-central1 \ --limit=50
Monitoring — alerts & uptime checks
# List alert policies gcloud alpha monitoring policies list # Create uptime check for a Cloud Run URL gcloud monitoring uptime create my-app-check \ --display-name="My App Health" \ --http-check-path=/health \ --hostname=my-service-xyz.run.app # Most monitoring is done in Cloud Console UI # or via Terraform — gcloud support is limited
Structured logging from Python — makes logs queryable in Cloud Logging
# In your Cloud Function / Cloud Run app import logging, json # Plain string log (works but hard to filter) logging.info("Loaded 500 rows from blob.csv.gz") # Structured log (preferred) — each key becomes a queryable field logging.info(json.dumps({ "message": "blob loaded", "blob": "optionchain/20260517.csv.gz", "rows": 500, "ticker": "BTC" }))
GUIDE

Decision guide — which compute service to use

SituationUseWhy
Scheduled job, simple crawler, event handler Cloud Functions No container needed, auto-scales to zero, cheapest for infrequent runs
HTTP API with a web framework (FastAPI, Flask) or WebSockets Cloud Run Bring your own container, handles sustained traffic, still serverless
Static web app (React, Vue) Firebase Hosting CDN-backed, free tier, instant deploys with firebase deploy
ML training job (GPU, long-running) Vertex AI Custom Job Managed GPU machines, billed per second, result saved to GCS
Always-on service, GPU inference, stateful app GKE Full Kubernetes control, reserved nodes, handles anything Cloud Run can't
Trigger X immediately when Y happens Pub/Sub Event-driven, decoupled — better than polling on a schedule
Store credentials / API keys Secret Manager Versioned, audited, injected into functions at deploy — never in code
Relational data (users, transactions, small rows) Cloud SQL (Postgres/MySQL) ACID transactions, row-level updates — BigQuery is for analytics, not OLTP
Analytics, feature store, ML input data BigQuery Columnar, petabyte-scale, cheap storage, fast aggregate queries
Raw files, model weights, CSV dumps Cloud Storage Object store, ~$0.02/GB/month, unlimited size
